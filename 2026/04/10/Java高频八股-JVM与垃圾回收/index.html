1. G1 和 CMS 垃圾回收器（5 场被问）⭐⭐⭐⭐

垃圾回收器分类

CMS 垃圾回收器

CMS（Concurrent Mark Sweep）是以最短停顿时间为目标的收集器。

什么是 STW？

STW（Stop The World） = 停止所有用户线程，暂停业务执行。

为什么需要 STW？

  • GC 时需要检查对象引用关系
  • 如果用户线程同时运行，对象引用可能随时变化
  • 暂停用户线程 → 引用关系稳定 → GC 准确

STW 的影响：

  • 停顿时间 = 应用无响应时间
  • STW 越长，用户体验越差
  • 高频 STW → 服务延迟高

回收过程（4 步）：

CMS 的问题：

  • CPU 资源占用：并发阶段占用 CPU，影响吞吐量
  • 浮动垃圾：并发标记期间产生的垃圾无法清理
  • 内存碎片：使用标记-清除，产生碎片，需要 Full GC 整理

CMS 适合场景：

  • 注重响应时间的应用
  • 老年代大于年轻代的场景

G1 垃圾回收器

G1（Garbage First）是 JDK9 默认的垃圾回收器，采用分区式设计。

核心概念：

回收过程（4 步）：

G1 的分区原理

Region 大小：

  • -XX:G1HeapRegionSize：每个 Region 的大小（2的幂次，1MB~32MB）

大对象（Humongous Objects）：

  • 超过 Region 50% 的大对象
  • 单独存放在 Humongous 区
  • 老年代回收时处理

**Remembered Set (RSet)**：

  • 每个 Region 维护一个 RSet，记录其他 Region 对本 Region 的引用
  • 用于可达性分析时快速定位对象

STW 时间配置

注意：这个值是目标，不是硬性保证。G1 会尽量达成，但无法保证。

200ms vs 500ms 取舍：

配置 目标 适用场景
-XX:MaxGCPauseMillis=200 低延迟要求 Web 服务、API 接口
-XX:MaxGCPauseMillis=500 高吞吐量 批处理、后台计算
  • 小值（200ms）：GC 频繁，吞吐量降低，但响应更快
  • 大值（500ms）：GC 次数减少，吞吐量高，但单次停顿长

为什么吞吐量大的场景可以牺牲 STW 时间？

吞吐量场景：批处理、离线计算、大数据处理

结论：对于一次性任务，长停顿可以接受，提高吞吐量更重要。

CMS 和 G1 的核心区别

特性 CMS G1
内存模型 物理分代（年轻代/老年代连续） 分区（多个 Region）
收集方式 标记-清除 标记-整理
内存碎片 有碎片 无碎片（整理）
STW 时间 较长（Full GC 时） 可控（通过 MaxGCPauseMillis）
大对象处理 直接放老年代 单独 Humongous 区
JDK 版本 JDK8 及以前常用 JDK9+ 默认
并发标记 单一并发 并发 + 混合回收

选择建议：

  • JDK8 及以前：CMS
  • JDK9+：G1
  • 追求低延迟：G1
  • 追求高吞吐量：Parallel Old + Parallel Scavenge

3. JDK 内存结构（2 场被问）⭐⭐⭐

JDK8 内存模型

年轻代和老年代

年轻代（Young Generation）：

  • 存放新创建的对象
  • 对象生命周期短，频繁回收
  • 分为：Eden 区 + 2 个 Survivor 区（S0、S1）

老年代（Old Generation）：

  • 存放长期存活的对象
  • 对象经过多次 Minor GC 后晋升到老年区
  • 回收频率低，但回收耗时较长

堆和方法区的区别

区域 堆 方法区
存储内容 对象实例、数组 类信息、运行时常量池、静态变量、JIT 编译产物
线程共享 是 是
垃圾回收 频繁（年轻代/老年代） 较少（主要回收废弃常量和无用的类）
内存溢出 常见（OOM: Java heap space） 较少（OOM: Metaspace）
JDK8 以前 堆 PermGen（永久代）
JDK8 以后 堆 Metaspace（元空间）

4. 双亲委派机制（2 场被问）⭐⭐

双亲委派是什么？

定义：类加载器收到加载请求时，先委派给父类加载器处理，只有父加载器无法完成时才自己加载。

加载流程：

为什么要双亲委派？

  1. 避免类重复加载：父加载器已加载，子加载器不再加载
  2. 保证安全性：防止用户自定义类替换 JDK 核心类
  3. 保证一致性：相同类名始终映射到同一个类

5. 虚拟线程（JDK21）（2 场被问）⭐⭐

虚拟线程和平台线程的区别

平台线程（传统线程）：

  • 1:1 映射：1 个 Java 线程 = 1 个 OS 线程
  • 由 OS 调度，阻塞时占用 OS 线程资源

虚拟线程：

  • M:N 映射：M 个虚拟线程映射到 N 个 OS 线程（平台线程）
  • 由 JVM 调度，阻塞时让出 OS 线程

对比

特性 平台线程 虚拟线程
创建成本 高（需要 OS 分配） 低（轻量级）
内存占用 1MB+ 栈 几百字节~几MB（动态）
调度 OS 调度 JVM 调度
阻塞行为 阻塞 OS 线程 让出 OS 线程
数量限制 几百~几千 数十万~数百万
适用场景 计算密集型 IO 密集型

虚拟线程的限制

面试常问

Q：虚拟线程和线程池的区别？

  • 线程池：复用有限数量的平台线程
  • 虚拟线程：每个任务都是新虚拟线程，平台线程按需分配

Q：虚拟线程适合什么场景？

  • 大量并发 IO 任务（HTTP、数据库调用）
  • 不适合：CPU 密集型计算（仍需平台线程）

Q：虚拟线程为什么高效？

  • 减少内存占用（按需分配栈）
  • 减少上下文切换（阻塞时让出 Carrier 线程）
  • 高并发 IO 场景下，一个 Carrier 线程可服务大量虚拟线程
