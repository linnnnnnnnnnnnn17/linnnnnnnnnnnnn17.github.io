1. 线程池的核心参数和原理（14 场被问）⭐⭐⭐⭐⭐

核心参数

四个核心参数作用

  1. corePoolSize（核心线程数）：线程池长期维持的最小线程数。即使空闲也不会销毁，除非设置 allowCoreThreadTimeOut(true)

  2. maximumPoolSize（最大线程数）：线程池允许创建的最大线程数

  3. workQueue（等待队列）：存放待执行任务的阻塞队列

    • ArrayBlockingQueue：有界队列
    • LinkedBlockingQueue：无界队列（慎用，可能导致 OOM）
    • SynchronousQueue：直接提交队列，不存储任务

  4. handler（拒绝策略）：

    • AbortPolicy：抛异常（默认）
    • CallerRunsPolicy：由调用方线程执行
    • DiscardPolicy：丢弃任务
    • DiscardOldestPolicy：丢弃队列最老的任务

工作原理

常见追问

Q1：IO 密集型和 CPU 密集型分别怎么配？

  • CPU 密集型：核心线程数 = CPU 核心数 + 1（避免频繁上下文切换）
    • 公式：Runtime.getRuntime().availableProcessors() + 1
  • IO 密集型：核心线程数 = CPU 核心数 × 2（IO 等待时间长，可多配置线程）
    • 或 CPU 核心数 / (1 - 阻塞系数)，阻塞系数通常 0.8~0.9

Q2：无界队列会导致什么问题？

  • 内存无限膨胀导致 OOM（Out Of Memory 内存溢出）
  • 即使最大线程数已设置，队列无限增长无法触发扩容
  • 拒绝策略永远不会执行

什么是 OOM？

OOM（Out Of Memory）即内存溢出，指 JVM 运行时无法分配足够的内存，导致 OutOfMemoryError 异常。

无界队列 OOM 原因：

常见 OOM 类型：

类型 原因
Java heap space 堆内存不足（如无界队列）
GC overhead limit exceeded GC 时间过长
Metaspace 元空间不足
Unable to create new native thread 线程数过多

解决思路：

  • 使用有界队列：new LinkedBlockingQueue<>(1000)
  • 合理设置 corePoolSize 和 maximumPoolSize
  • 开启堆转储分析：-XX:+HeapDumpOnOutOfMemoryError

Q3：空闲线程怎么回收？

  • 超过 keepAliveTime 且线程数 > corePoolSize，会被销毁
  • 可通过 allowCoreThreadTimeOut(true) 让核心线程也可回收

Q4：队列满了为什么先入队而不是先扩容线程？

  • 队列未满说明任务处理速度足够，优先复用现有线程成本更低
  • 扩容线程需要创建新线程，开销较大
  • 队列满时再扩容，防止任务堆积时频繁创建线程

3. CAS 与 ConcurrentHashMap（6 场被问）⭐⭐⭐⭐

CAS 原理

CAS（Compare And Swap）包含三个操作数：

  • 内存位置 V
  • 预期值 A
  • 新值 B

执行过程：只有当 V 的值等于 A 时，才将 V 更新为 B；否则不做任何操作。CAS 是乐观锁，适用于冲突较少的场景。

ABA 问题

问题本质：CAS 只检查”值是否变化”，但不关注值的变化过程。

你说得对，单纯从值来看好像没影响。但 ABA 问题的关键在于：值相同不代表状态没变化。

ABA 为什么重要：

  • 单纯值一样，但对象引用可能变了
  • 栈/队列的结构可能变了
  • 某些操作依赖”中间状态”，但 CAS 感知不到中间过程

常见受影响场景：

  • 栈的 push/pop：top 节点可能被重新替换
  • 链表操作：中间节点被移除又插入
  • 分布式乐观锁：版本号变化但数据更新了

解决：用 AtomicStampedReference 同时比较值和版本号

ConcurrentHashMap 为什么同时用 CAS 和 synchronized？

  • JDK7：Segment 分段锁，每个 Segment 独立加锁
  • JDK8：取消分段锁，使用 synchronized 锁头节点，其余节点用 CAS
操作 使用技术
数组初始化 CAS
扩容 synchronized 锁头节点
插入/删除/更新 synchronized 锁头节点 + CAS 更新值
读取 无锁（volatile）

原因：CAS 适合简单操作（数组初始化），synchronized 适合复杂操作（链表/红黑树操作），两者结合扬长避短。

并发度 高（分段锁/桶锁） 低（全局锁）

4. ThreadLocal 原理和内存泄漏（5 场被问）⭐⭐⭐⭐

原理

每个 Thread 有一个 ThreadLocalMap，本质是一个 Entry 数组。ThreadLocal 作为 key（弱引用），value 为存储的值。

为什么 key 用弱引用，value 用强引用？

  • key（ThreadLocal）弱引用：当 ThreadLocal 变量不再被外部引用时，可以被回收，避免 key 永远存在导致内存泄漏
  • value 强引用：防止 value 被意外回收

强引用 vs 弱引用

特性 强引用 弱引用
定义 Object obj = new Object() WeakReference<T> ref = new WeakReference<>(obj)
GC（垃圾回收）回收 不会被自动回收 只能存活到下一次 GC
内存 即使 OOM 也不回收 内存紧张时优先回收
场景 正常对象引用 缓存、Map key 等可回收场景

什么是 GC（垃圾回收）？

GC（Garbage Collection）即垃圾回收，是 JVM 自动回收不再使用的内存的机制。

GC 回收对象的前提：

  • 该对象没有任何强引用指向它
  • 或者只被弱引用/软引用/虚引用指向

5. volatile 关键字（5 场被问）⭐⭐⭐⭐

两大特性

  1. 可见性：一个线程修改 volatile 变量，其他线程立即可见
  2. 有序性：禁止指令重排序（volatile 前的代码不能重排到 volatile 后，volatile 后的代码不能重排到 volatile 前）

底层原理

  • 写操作时，强制将值刷新到主内存
  • 读操作时，强制从主内存读取最新值
  • 插入内存屏障（Store屏障、Load屏障），禁止指令重排

volatile 能不能替代锁？

不能完全替代，volatile 只保证可见性和有序性，不保证原子性。

能用 volatile 的场景：

  • 状态标志：volatile boolean running = true;
  • 双重检查锁中的对象引用
  • 单例模式的 INSTANCE

双重校验锁必须用 volatile

为什么要 volatile？
INSTANCE = new Singleton(); 分为 3 步：

  1. 分配内存
  2. 调用构造函数
  3. 赋值给 INSTANCE

重排序后可能发生：先赋值（2），后初始化（1），其他线程拿到未初始化对象 → 引用逃逸

场景选择

场景 用 volatile 用 synchronized/Lock
状态标记 ✅ ❌
单次赋值后不再变 ✅ ❌
计数/累加 ❌ ✅
复合操作 ❌ ✅

什么是 AQS？

AQS（AbstractQueuedSynchronizer）是 JDK 并发包的核心组件，抽象队列同步器。

  • 实现了锁的排队等待机制

9. wait/sleep/notify（2 场被问）⭐⭐

wait 和 sleep 的区别

特性 wait() sleep()
所属 Object Thread
锁释放 ✅ 释放 monitor 锁 ❌ 不释放锁
响应中断 ✅ 抛 InterruptedException ✅ 抛 InterruptedException
需在 synchronized ✅ 必须 ❌ 不需要
超时自动唤醒 ✅ ✅

notify 和 notifyAll 的区别

  • notify()：唤醒一个等待该锁的线程（不确定唤醒哪个）
  • notifyAll()：唤醒所有等待该锁的线程

为什么通常用 notifyAll？

  • notify 可能导致只有部分线程被唤醒，其他线程永久等待
  • notifyAll 最终只有一个线程获得锁，其他继续等待，但更安全

为什么 wait 要在 synchronized 块里？

原因：

  1. wait() 必须先获取对象的 monitor 锁，否则抛 IllegalMonitorStateException
  2. wait() 会释放锁，其他线程可以进入 synchronized 块
  3. 配合 while 循环防止伪唤醒（spurious wakeup）

线程池大小如何设置？

synchronized 锁升级过程？

无锁 → 偏向锁 → 轻量级锁 → 重量级锁

  • 偏向锁：首次获取，Mark Word 记录线程 ID
  • 轻量级锁：自旋 CAS 抢锁
  • 重量级锁：自旋失败，挂起线程

ReentrantLock 可重入原理？

可重入：同一线程可以多次获取同一把锁，不会被自己阻塞。

执行流程图解：

为什么可重入？

  • 第一次 lock.lock()：state 从 0 变为 1
  • 第二次 lock.lock()（重入）：state 从 1 变为 2
  • unlock()：state 减 1，直到 state 变为 0 才真正释放锁

state 的含义：

  • state = 0：无锁
  • state > 0：已获取锁，值 = 重入次数
  • unlock() 会把 state 减 1，直到 0 才释放

特性 CountDownLatch CyclicBarrier
作用 主线程等待 n 个子线程 n 个线程相互等待

能否重置 ❌ 不可重置 ✅ 可重置
典型场景 主线程等待子线程完成 多线程相互等待

线程状态转换

  • RUNNABLE：就绪/运行
  • BLOCKED：等待获取 monitor 锁
  • WAITING：Object.wait()/Thread.join()/LockSupport.park()
  • TIMED_WAITING：sleep()/wait(timeout)/join(timeout)/parkNanos()

11. final 关键字 ⭐⭐⭐

final 的作用

final 表示不可改变，可以修饰：

  • 类：不能被继承
  • 方法：不能被重写
  • 变量：不能被重新赋值

1. 修饰类

为什么 String 是 final 的？

  • 安全性：防止子类重写方法改变字符串行为
  • 性能：JVM 可以对 final 类做更多优化（内联等）
  • 不可变性：保证字符串创建后不会改变

2. 修饰方法

为什么用 final 方法？

  • 防止子类修改父类的关键行为
  • 允许 JVM 进行方法内联优化（方法调用变为直接展开代码）

面试常问

Q：final 关键字在 Java 中有什么作用？

  • 修饰类：禁止继承
  • 修饰方法：禁止重写，允许内联优化
  • 修饰变量：禁止重新赋值（基本类型值不变，引用类型引用不变）

Q：final 能保证线程安全吗？

  • 不能！final 只保证初始化安全，不保证使用安全
  • 例子：final List<String> list 本身可以 add/remove，不是线程安全的
