一、分布式锁（6 场被问）⭐⭐⭐⭐⭐

分布式锁：用于在多台机器/多个进程间保证同一时刻只有一个进程能访问共享资源。

场景：多机器部署的微服务，同时抢优惠券、扣库存等

特点：

  • 跨 JVM（不同进程/机器）
  • 互斥：只能一个线程获取
  • 防死锁：超时自动释放
  • 可重入：同一线程可多次获取

  • EX：设置过期时间（防止锁无法释放）

策略：

  3. 排队等待：进入消息队列，等锁释放后通知
  4. 降级处理：兜底方案，保证最终一致性

2.4 限流会不会有性能问题（CAS vs 锁竞争）

CAS 自旋导致 CPU 空转的具体情况：

问题场景：

  • 10000 个请求同时抢令牌
  • 只有 1 个成功，9999 个继续循环
  • 每个线程每秒循环几十万次
  • CPU 很高但全是无效计算

对比锁竞争：

  • CAS：用户态循环，CPU 高但省调度
  • 锁：内核态等待，CPU 低但有上下文切换

解决方案：

  1. 令牌桶预热：提前放入令牌
  2. 多桶策略：分散请求
  3. 本地限流 + 分布式兜底：减少 Redis 交互
  4. 消息队列削峰：异步处理

4.1 三者的区别

类型 原因 结果 解决方案
缓存穿透 查询不存在的数据 数据库压力变大 布隆过滤器、空值缓存

4.2 布隆过滤器原理和误判率

布隆过滤器：一种高效判断数据是否存在的数据结构，用于解决缓存穿透

核心思想：用一个大数组 + 多个 Hash 函数

示例（数组长度 10，3 个 Hash 函数）：

判断是否存在：

  • 查询 “用户1”：看位置 1、5、8 是否都是 1 → 是 → 可能在
  • 查询 “用户3”：看位置 2、4、6 是否都是 1 → 否 → 一定不存在

为什么会有误判：

  • 位置 5 被用户 1 和用户 2 共用（冲突）
  • 查询时发现位置 5 是 1，就以为是用户 2
  • 其实可能是用户 1 占用的位置

特点：

  • 说存在：可能存在（误判）
  • 说不存在：一定不存在（准确）

公式推导：

自然常数 e ≈ 2.718

第一步：单个位置未被写入的概率

存 n 个数据时，一个位置没被 Hash 命中的概率：

结果：n 次写入后，一个位置仍未被标记的概率 ≈ e^(-n/m)

第二步：被标记的概率 = 1 - e^(-n/m)

问题1：为什么 (1 - e^(-n/m) )^k = (1 - e^(-kn/m) )^k

k 个 Hash 函数，每个函数独立处理 n 个数据。

  • 第一个 Hash 函数处理 n 个数据 → 未被标记概率 e^(-n/m)
  • 第二个 Hash 函数处理 n 个数据 → 未被标记概率 e^(-n/m)
  • …
  • 第 k 个 Hash 函数处理 n 个数据 → 未被标记概率 e^(-n/m)

k 个 Hash 函数都未被标记的概率：

纠错：之前的推导有误！

错误推导：

  • 误以为每个 Hash 函数独立处理 n 个数据
  • 把 k 个函数简单相乘得到 (1 - e^(-n/m))^k

正确推导：

  • n 个数据 × k 个 Hash 函数 = n×k 次写入
  • 直接按总写入次数计算

标准误判率公式（正确推导）：

存入 n 个数据，每个数据 k 个 Hash 函数，总共 n×k 次写入。

  • 单个位置未被任何写入的概率 = (1 - 1/m)^(kn)
  • 单个位置被至少写入一次的概率 = 1 - (1 - 1/m)^(kn)
  • k 个位置都被写入的概率 = [1 - (1 - 1/m)^(kn) ]^k
