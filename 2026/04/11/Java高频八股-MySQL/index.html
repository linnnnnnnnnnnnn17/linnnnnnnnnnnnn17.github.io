一、索引与 B+ 树（8 场被问）⭐⭐⭐⭐⭐

1.1 联合索引的最左前缀匹配

原理：联合索引遵循”最左前缀匹配”原则，即查询从索引的最左列开始依次向右匹配，只要跳过了某一列，后续列的索引就无法使用。

示例：联合索引为 (a, b, c)

  • ✅ WHERE a = 1 可用索引
  • ✅ WHERE a = 1 AND b = 2 可用索引
  • ✅ WHERE a = 1 AND b = 2 AND c = 3 可用索引
  • ❌ WHERE b = 2 不可用（跳过 a）
  • ❌ WHERE a = 1 AND c = 3 只用到 a 列（b 列未使用）

底层原因：B+ 树的叶子节点按 (a, b, c) 顺序存储，跳过 a 就无法定位。

1.2 覆盖索引和回表

覆盖索引：查询所需的列全部在索引中，无需回表。

回表：查询的列不在索引中，需要先通过索引找到主键，再通过主键去主键索引树查找完整行数据。

1.3 B+ 树和 B 树的区别

特性 B+ 树 B 树
数据存储位置 仅叶子节点存储数据 所有节点都存储数据
叶子节点链表 叶子节点用指针相连 无连接
查询稳定性 稳定 O(logN)，所有查询都要到叶子 不稳定，可能在任意节点找到
磁盘 IO 只需访问叶子节点，IO 次数少 每个节点都可能包含数据，IO 次数多
范围查询 通过叶子节点链表高效 需要遍历所有节点

为什么 MySQL 用 B+ 树而非 B 树：

  1. 磁盘 IO 次数更少（树高度更低）
  2. 查询稳定（都要到叶子节点）
  3. 范围查询高效（叶子节点链表）

B+ 树层级计算：

  • 假设每个非叶子节点可存 1200 个指针（MySQL 16KB 页 / 12B 约值）
  • 叶子节点可存 15 条数据（假设每行 1KB）
  • 层级计算公式：总数据量 / (1200^层级-1 * 15)
  • 示例：20 亿数据约需 4 层（2000000000 / 1200^3 / 15 ≈ 3.1 层 → 4 层）

索引查询过程：

  1. 加载根节点到内存，通过二分查找定位到子节点
  2. 加载子节点，重复二分查找定位
  3. 逐层向下，直到叶子节点
  4. 叶子节点中获取数据（若是聚簇索引则直接获取数据，若是二级索引则获取主键值）
  5. 若需要回表，根据主键值加载聚簇索引获取完整行数据

1.4 聚簇索引和非聚簇索引

InnoDB：MySQL 默认的存储引擎，支持事务、行级锁、外键。采用索引组织表（Index Organized Table，IOT），数据行以主键顺序物理存储。

常见存储引擎：

引擎 特点 适用场景
InnoDB 支持事务、行级锁、外键 生产环境（默认）
MyISAM 不支持事务、表级锁 只读/静态表
Memory 内存存储 临时表、缓存
Archive 压缩存储 日志、归档

聚簇索引：数据行的物理顺序与索引顺序相同，一个表只有一个聚簇索引。

  • InnoDB 中主键索引就是聚簇索引
  • 如果没有主键，选择第一个唯一非空索引
  • 如果都没有，生成隐藏的 rowid 作为聚簇索引

非聚簇索引（二级索引/辅助索引）：

  • 索引树中存储的是主键值，而非数据行
  • 查询时需要回表（如果列不在索引中）

1.5 索引是不是越多越好

不是，索引有以下代价：

  1. 空间代价：每个索引都是一棵 B+ 树，需要额外存储空间
  2. 维护代价：增删改时需要维护所有索引
  3. 写入变慢：INSERT/UPDATE/DELETE 需要同时更新多个索引

原则：

  • 索引建立在高频查询字段上
  • 区分度高的字段（基数大，如 user_id）
  • 避免建立过多索引
  • 复合索引代替单列索引

1.6 覆盖索引还会回表的情况（MVCC 相关）

在某些情况下，即使使用了覆盖索引，仍可能回表：

原因：MVCC 机制下的一致性非锁定读

当执行 UPDATE/DELETE 或使用 SELECT ... FOR UPDATE 时，需要读取行的最新数据来检测并发冲突，此时会进行锁定读，触发回表获取最新数据。

二、事务、隔离级别与 MVCC（6 场被问）⭐⭐⭐⭐

2.1 四种隔离级别及实现方式

隔离级别 中文名 脏读 不可重复读 幻读 实现方式
READ UNCOMMITTED 读未提交 ✅ ✅ ✅ 无锁，直接读未提交数据
READ COMMITTED (RC) 读已提交 ❌ ✅ ✅ 快照读（每条 SELECT 生成新 ReadView）
REPEATABLE READ (RR) 可重复读 ❌ ❌ ✅ 快照读（事务开始生成 ReadView）
SERIALIZABLE 串行化 ❌ ❌ ❌ 锁（所有读都加锁）

实现原理：

  1. READ UNCOMMITTED：直接读取其他事务未提交的数据
  2. READ COMMITTED：每次 SELECT 都生成新的 ReadView
  3. REPEATABLE READ：事务开始时生成 ReadView，整个事务复用
  4. SERIALIZABLE：所有读操作都加 LOCK IN SHARE MODE

2.2 MVCC 和 ReadView 的关系

MVCC（Multi-Version Concurrency Control）：多版本并发控制，通过保存数据的多个版本来实现并发读写。

ReadView：快照读的核心，包含：

  • m_ids：活跃事务列表（未提交的事务）
  • min_trx_id：最小活跃事务 ID
  • max_trx_id：创建快照时最大事务 ID + 1
  • creator_trx_id：当前事务 ID

2.3 RC 和 RR 的区别

特性 READ COMMITTED REPEATABLE READ
ReadView 生成时机 每次 SELECT 事务开始时
不可重复读 可能发生 避免发生
幻读 可能发生 可能发生（需 Gap 锁）
并发度 更高 较低

核心区别：RC 每次读取都生成新 ReadView，RR 整个事务复用同一个 ReadView。

2.4 事务的 ACID 各自靠什么机制保证

特性 机制
Atomicity（原子性） A undo log（回滚日志）
Consistency（一致性） C 引擎层（InnoDB）+ 应用层共同保证
Isolation（隔离性） I MVCC + 锁
Durability（持久性） D redo log + 刷盘策略

三、分库分表（3 场被问）⭐⭐⭐

3.1 什么场景用分库分表 vs 加索引就够了

加索引就够的场景：

  • 数据量 < 千万级别
  • 查询可以命中索引
  • 单表性能足够

需要分库分表的场景：

  • 数据量 > 千万级，查询开始变慢
  • 单库磁盘或连接达到瓶颈
  • 单表过大，DDL 操作耗时过长

3.2 数据量几十亿即使有索引还是慢的原因

B+ 树层级变深：即使有索引，几十亿数据会导致 B+ 树层级达到 4-5 层，每次查询需要 4-5 次磁盘 IO。

计算：假设每个叶子节点 1KB，几十亿数据可能需要 3-4 层索引。

3.3 分库分表中间件怎么实现

实现方式：通过 AOP 拦截 SQL，修改 SQL 语句中的表名，实现分布式路由。

常见中间件：ShardingSphere、MyCat、Sharding-JDBC

3.4 没有分表键的查询怎么处理

方案：

  1. 异步双写：写原表 + 写汇总表
  2. 打宽表：将多个分表数据汇总到一张表
  3. 异构索引：建立搜索 SOLR/ES
  4. 直接查所有分表：广播到所有分表查询（牺牲性能）

四、慢查询与深分页优化（3 场被问）⭐⭐⭐

4.1 分页查询变慢的原因

原因：LIMIT OFFSET 语法需要先扫描 OFFSET 条数据，然后丢弃前 OFFSET 条，再取 LIMIT 条。

4.2 游标分页（ID 记录法）

原理：使用主键或索引列作为游标，记录上次查询的最后一条 ID。

4.3 EXPLAIN 怎么分析执行计划

关键字段：

  • type：访问类型
  • key：使用的索引
  • rows：预计扫描行数
  • Extra：Using filesort / Using temporary 等

访问类型详解（从最优到最差）：

访问类型 说明 场景
const 常量访问，最多一条匹配 主键或唯一索引等值查询
eq_ref 唯一索引等值扫描 关联查询使用主键/唯一索引
ref 非唯一索引等值扫描 普通索引等值查询
range 索引范围扫描 BETWEEN、>、<、LIKE 等
index 全索引扫描 覆盖索引 ORDER BY
ALL 全表扫描 最慢，需要避免

Extra 常见值：

值 说明
Using filesort 需要额外排序（ ORDER BY 字段无索引）
Using temporary 使用临时表（ GROUP BY/DISTINCT 字段无索引）
Using index 覆盖索引，无需回表
Using where 使用 WHERE 过滤
Using index condition 使用索引下推（ICP）

4.4 一个事务中有多条慢语句怎么排查

  1. 开启慢查询日志：slow_query_log = 1
  2. 设置阈值：long_query_time = 1
  3. 分析慢查询日志
  4. 使用 EXPLAIN 分析每条语句
  5. 使用 SHOW PROCESSLIST 查看当前连接

五、redo log / binlog / undo log（3 场被问）⭐⭐⭐

5.0 基础概念

刷盘：将内存中的数据写入磁盘。直接刷盘是随机写入，性能较差。

redo log（重做日志）：

  • 作用：记录物理页的修改，用于崩溃恢复
  • 位置：InnoDB 引擎层
  • 写入：事务执行中，顺序写入 Redo Log Buffer，再刷到磁盘

示例：UPDATE user SET age = 20 WHERE id = 1

  • binlog 记录：update user set age = 20 where id = 1
  • redo log 记录：page[表空间号:页号:偏移量] 把 age 从 18 改成 20（物理页级别的修改）

binlog（二进制日志）：

  • 作用：记录 SQL 语句，用于数据备份、主从同步
  • 位置：MySQL Server 层
  • 写入：事务提交时，一次性写入

undo log（回滚日志）：

  • 作用：记录反向操作，用于事务回滚和 MVCC
  • 位置：InnoDB 引擎层
  • 写入：事务执行中，记录旧值

5.1 redo log 为什么存在（为什么不直接刷盘）

原因：

  1. 随机写改顺序写：redo log 是顺序写入，比直接刷盘快
  2. 减少 IO 次数：redo log 累积后再刷盘，减少 IO
  3. 崩溃恢复：redo log 记录修改，用于崩溃后恢复

5.2 redo log 和 binlog 的区别

特性 redo log binlog
所在层次 InnoDB 引擎层 MySQL Server 层
记录内容 物理页的修改 SQL 语句
写入时机 事务执行中 事务提交时
用途 崩溃恢复 数据备份、主从同步

5.3 undo log 在 Insert 和 Update 时分别记什么

Insert：记录插入的数据主键，方便回滚时删除

Update：记录修改前的数据（旧值），回滚时恢复旧值

本质：undo log 是反向操作日志，用于实现事务回滚和 MVCC。
