1. 为什么需要智能指针：RAII

1.1 核心思想

RAII（Resource Acquisition Is Initialization）：资源的获取与释放绑定到对象的构造与析构。

  • 构造时获取资源（如new、open、lock）
  • 析构时自动释放（如delete、close、unlock）
    无论正常return还是异常，只要对象析构，资源一定被释放

1.2 裸指针的典型问题


问题：多出口、异常时容易漏删；且p的地址在每次运行可能不同，调试时只能看到“某块堆地址”，难以和“谁拥有、何时释放”对应。
用RAII封装后，谁拥有资源和何时释放一目了然，且与地址打印、断点调试兼容。

1.3 RAII 封装示例

调试建议：在构造/析构处打断点，观察m_data的地址；return时确认析构被调用、同一地址只被释放一次。

2. unique_ptr：独占所有权

2.1 原理简述

  • 一个资源在同一时刻只被一个unique_ptr拥有。
  • 禁止拷贝，只允许移动；移动后源指针置空，所有权转移。
  • 内部本质上就是一个“带析构的裸指针”，析构时对持有指针做delete或delete[]。

2.2 内存视角

调试：对p1.get()、p2.get()监视或打印，可见移动前两者指向同一地址，移动后p1.get()为nullptr，p2.get()仍为原地址。

2.3 推荐用法：make_unique（C++14）

2.4 内部实现逻辑

  • 独占性：通过删除拷贝、只保留移动实现。拷贝构造与拷贝赋值被标为=delete，因此不能拷贝；移动构造与移动赋值将源指针“窃取”并置空，保证同一时刻只有一个unique_ptr持有该指针。
  • 成员：通常仅有一个成员——指向所管理对象的指针（以及可能内嵌的删除器类型，无状态删除器时大小仍为一个指针）。
  • 析构：析构时对持有的指针调用删除器（默认delete），不涉及引用计数。

2.5 局限与注意

  • 不能拷贝，只能移动；不适合“多个所有者”共享同一对象。
  • 用get()得到裸指针时，不要对这块内存做delete，也不要再交给别的智能指针管理，否则重复释放。
  • 数组用unique_ptr<int[]>或std::vector，避免误用unique_ptr<int>配new int[n]。

3. shared_ptr：共享所有权与引用计数

3.1 原理简述

多个shared_ptr可以指向同一对象，内部维护一个控制块（通常包含引用计数、弱引用计数、deleter等）。
拷贝/赋值时引用计数 +1，析构或重置时 -1；当计数变为 0 时执行delete（或自定义deleter）。
控制块和对象一般都在堆上；调试时既可看“对象地址”，也可通过use_count()推断有多少个shared引用。

3.2 代码与 use_count / 地址

3.2.1 调试

调试建议：
监视p1.get()、p2.get()（应相同）、p1.use_count()。
在return 0前断点，确认use_count() == 1，再单步到main结束，观察析构只发生一次。

3.2.2 一些调试的发现

  • 不在变量作用域时，监视的值这一栏会写 未定义标识符xxx，而在作用域但还未初始化时，get() 的值显示的是0xccccccc...，和之前 debug_practice 时查到的下述语句相呼应。

编译器会自动把未初始化的栈内存填充为 0xCC

  • 在作用域但还未初始化时，use_count() 的值显示的是 由于发生未经处理的异常，计算已中止。

  • 手动重置的shared_ptr（即此处的 p2）地址变为0，计数也变为0。系统自动在 return 0 后执行析构的 p1 的get() 没有变，但是 *p1 和 use_count 都变成了无效垃圾值-572662307，证明对应的内存已被释放。从内存窗口查看显示的是dd dd dd dd，是VS 在 Debug 模式下，对已释放堆内存的标准填充值。

3.3 应用场景

多处代码需要“共享”同一对象，且没有明确单一所有者。
例如：多个模块持有同一配置对象、同一网络连接、同一缓存块等。

3.4 引用环（循环引用）

当A持有B的shared_ptr，B又持有A的shared_ptr时，形成环，引用计数永不为0，对象永不析构，造成泄漏。

解决：环上某一侧改用weak_ptr。

3.5 内部实现逻辑

成员与内存布局（以libstdc++为例）：
shared_ptr<T>内部只有两个指针成员：

  • 一个指向所管理对象（element_type* _M_ptr）；
  • 一个指向控制块（__shared_count，内部再持有引用计数等）。
    控制块一般在堆上，包含：引用计数、弱引用计数（供weak_ptr用）、**删除器(Deleter)、分配器(Allocator)**。多个shared_ptr共享同一对象时，共享同一控制块，因此引用计数也在堆上。
    因此shared_ptr对象大小约为裸指针的两倍；unique_ptr通常只有一个裸指针，大小为裸指针的一倍。 引用计数的简化实现（仅用int*表示计数，便于理解“何时+1/-1、何时delete”）：
  • 拷贝/赋值：复制“对象指针+控制块指针”，引用计数+1。
  • 析构/reset()：引用计数-1；若变为0，则delete对象并释放控制块（此处简化版仅delete m_refCount）。

3.6 注意事项

尽量用make_shared<T>而不是shared_ptr<T>(new T)

  • make_shared<T>(args...)通常一次分配：对象与控制块在连续内存中分配，局部性更好，且只可能有一次分配失败。
  • shared_ptr<T>(new T(args...))是两次分配：先new T，再为控制块分配；若new T成功而控制块分配抛异常，已分配的对象可能无法被任何shared_ptr接管，存在泄漏风险。因此推荐默认使用make_shared。
    不要用同一裸指针初始化多个shared_ptr

4. weak_ptr：打破引用环

4.1 原理简述

  • weak_ptr 不增加引用计数，仅作为shared_ptr管理对象的“观察者”
  • 通过lock()方法获取有效的shared_ptr：对象存活则返回有效指针，否则返回空
  • 用expired()可先判断对象是否已释放，再决定是否调用lock()，避免无效操作

4.4 局限

  • weak_ptr不单独拥有资源，必须依赖shared_ptr；不能从裸指针或unique_ptr直接构造（需先转为shared_ptr）
  • 每次访问都需要lock()，有轻微开销；高频访问且生命周期可控时，用裸指针/引用更合适（需确保生命周期安全）

5. 局限总览

问题类型 核心说明 注意事项
性能开销 shared_ptr包含控制块和原子计数，比裸指针、unique_ptr略重 热路径、极致性能场景需权衡，优先用unique_ptr
循环引用 shared_ptr互相持有会导致计数永不为0，内存泄漏 必须用weak_ptr打破，设计时识别“谁该持有weak引用”
与裸指针混用 get()得到的裸指针禁止手动delete、禁止交给其他智能指针 外部保存裸指针时，必须保证其生命周期短于智能指针
不解决逻辑错误 智能指针仅管理资源释放，不解决多线程数据竞争 需配合mutex、原子操作等保证线程安全
循环依赖与模块边界 大工程中易出现隐蔽的shared_ptr环 尽量在一侧用weak_ptr，或明确单一所有者（unique_ptr+非拥有观察者）

6. Qt中的智能指针

6.1 常用类型与标准库对应关系

Qt类型 作用 对应C++标准库
QSharedPointer<T> 共享所有权，引用计数，最后一个引用销毁时删除对象；引用计数为线程安全 std::shared_ptr<T>
QWeakPointer<T> 弱引用，不增加引用计数，用toStrongRef()/lock()i提升为QSharedPointer<T>再使用 std::weak_ptr<T>
QScopedPointer<T> 作用域内独占所有权，不可拷贝，可移动；出作用域自动删除 std::unique_ptr<T>（C++11起）
QScopedArrayPointer<T> 针对数组的独占所有权，析构时delete[] std::unique_ptr<T[]>（C++11起）
QPointer<T> 仅用于QObject派生类，对象销毁后自动变为nullptr，不管理所有权 无直接对应，是“可自动置空的观察指针”
QSharedDataPointer<T>/QExplicitlySharedDataPointer<T> 实现Qt风格的隐式/显式共享数据（写时复制） 无直接对应，Qt特有的数据共享工具

6.2 使用选型指南

  • 独占、局部使用 → QScopedPointer<T>（或C++11的std::unique_ptr<T>）
  • 多处共享、不确定谁最后释放 → QSharedPointer<T>（或std::shared_ptr<T>）
  • 打破循环引用、仅观察不拥有 → QWeakPointer<T>（或std::weak_ptr<T>）
  • 只看某个QObject，不管生命周期，销毁后自动空 → QPointer<T>（仅限QObject派生类）
  • 实现Qt隐式共享数据类 → QSharedDataPointer<T>/QExplicitlySharedDataPointer<T>

6.3 实践 - 源码分析

可深入分析QPointer的源码实现，其核心是通过QObject的destroyed()信号，在对象销毁时自动将内部指针置空，实现安全访问；QSharedPointer的实现逻辑与std::shared_ptr高度一致，同样包含控制块、引用计数等核心设计。

💡 补充核心知识点

shared_ptr 关键细节

  • make_shared 优先原则：std::make_shared<T>() 一次分配对象+控制块，比shared_ptr<T>(new T)（两次分配）更高效、更异常安全
  • 线程安全：std::shared_ptr的引用计数操作是原子的，但对象本身的访问不是线程安全的，需额外加锁
  • 自定义删除器：支持传入自定义删除器，用于管理非new分配的资源（如文件句柄、socket）

unique_ptr 关键细节

  • 禁止拷贝，仅允许移动：通过删除拷贝构造/赋值实现，保证独占所有权
  • make_unique（C++14）：推荐用法，避免new直接暴露，异常安全
  • 数组支持：std::unique_ptr<T[]> 自动用delete[]释放，适合管理动态数组
